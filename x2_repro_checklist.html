红线

这几条不是建议，是已经定下的约束。下面任何一步跟它们冲突，都停下来问，别自己绕。

  • 不升级系统。不 apt upgrade、不 dpkg -i、不改 ~/.bashrc。这套 Jetson 的驱动和 ROS 版本一动就回不来。
  • 东西只放在 ~/Documents/czq/ 下。包括解包出来的 SDK、虚拟环境、模型缓存。
  • 厂商文件一字不改。agibot_x2_urdf/X2_URDF-v1.3.0/ 下的 x2_ultra.xml、scene.xml、x2_ultra.urdf，GR00T-X2 有代码在引用它们。要改就派生一份新的。
  • GR00T-X2 的 .venv 和 czq/xr-env 是两套环境，别混用。.venv 是用 xr-env 的 python 建的，所以 .venv/bin/python 指向 xr-env——但 site-packages 完全独立。gear_sonic/pyproject.toml 硬钉 numpy==1.26.4，而 xr-env 是 numpy 2.x，往任一边装东西都可能把另一边的数值栈弄坏。跑 GR00T-X2 就用它自己的 .venv，跑 XRoboToolkit 才 source setup/activate.sh。
  • 两边都要清掉 ROS 注入的 PYTHONPATH。~/.bashrc source 了 ROS Jazzy，它给每个 shell 塞进 /opt/ros/jazzy/lib/python3.12/site-packages；而这两套环境都是 Python 3.10，混用会出「import 成功但行为错乱」这类最难查的问题。setup/activate.sh 干的就是这件事（顺带设 BROWSER）；直接用项目 .venv/bin/python 时，用 env -u PYTHONPATH 起。
  • 别在 demo 跑着的时候碰 SDK。不调 xrt.init()，不跑自检脚本。两个 SDK session 会互相抢。
  • 机器人站着的时候绝不 kill deploy 的 tmux 会话。要停只能走下面 L4 里那条停止命令。

    grep -m3 RTF "${SIMSTACK_DIR:-$HOME/.cache/sonic/simstack_pc}/logs/deploy.log"
    本机实测：0.96~0.97 稳定——够用，不是坑 8 Jetson 上 steady state 实测 RTF 0.97 / 0.96 / 0.96 / 0.97。这是 4% 的稳定缺口，和 0.51 不是同一回事：
    0.51 是结构性的——渲染被塞进物理循环，实时因子腰斩，按墙钟推进的参考轨迹相当于以两倍速灌进物理，失稳被盖住。
    0.96 只是 CPU 紧张——实测占用最高的是物理桥（x2_mujoco_ros_bridge 约 0.67 核）和镜像窗口（约 0.58 核），加起来不到 2 核，离饱和还远，且这个量级藏不住失稳。
    想抠回 1.00 的杠杆是关掉宿主侧镜像窗口，但那是唯一的观察窗，为 4% 不值得。
    别只信日志——独立测一遍 bridge 在 :5570 上发布 地面真值的 pelvis qpos（JSON：{"sim_time":…, "pelvis_qpos_wxyz":[x,y,z,qw,qx,qy,qz]}，注意 z 在第三个位置）。用 CONFLATE 只取最新帧，比较 sim_time 与墙钟就能独立算出 RTF： 
    .venv/bin/python - <<'EOF'
import zmq, json, time
ctx = zmq.Context(); s = ctx.socket(zmq.SUB)
s.setsockopt(zmq.CONFLATE, 1)          # 只留最新帧，否则会读到积压队列
s.connect("tcp://127.0.0.1:5570"); s.setsockopt(zmq.SUBSCRIBE, b"robot_pose")
def latest():
    while True:
        raw = s.recv()
        if s.getsockopt(zmq.EVENTS) & zmq.POLLIN == 0:
            return json.loads(raw.split(b" ", 1)[1])
a = latest(); w0 = time.time(); time.sleep(8); b = latest()
print(f"RTF = {(b['sim_time']-a['sim_time'])/(time.time()-w0):.3f}")
EOF
    实测 0.964，与 bridge 自报一致。同一个流也能看机器人到底在不在动（pelvis 的 x/y/z 轨迹）。
    会骗你的数字 RTF 0.51 意味着物理跑在半速上：参考轨迹以两倍速灌进物理，把本该暴露的不稳定全藏起来。这个值是 SIM_VIEWER_MODE=container 造成的——它把渲染塞进物理循环里。别设这个变量。 现在默认用的是 host 侧只读的 sim_mirror_viewer.py，关掉那个窗口不会影响仿真。

  • 就算你已经 Ctrl-C 过了，也要跑这条。它会停掉 kplanner、watchdog、bridge、token service、pad bridge、x2sim 容器，并清扫 deploy 节点。

    ./gear_sonic/scripts/simstack_local.sh --stop

下游已实测打通 0/0

要三个 Motion Tracker 和一副头显。除头显之外的下游整条链路已在 2026-09-29 用一段现成 tape 无头显验证通过（见第 6 条）——所以这一级剩下的都是「插上头显就有」的事，不再是未知数。

  • 实时遥操要用 Pico SDK，所以是单独一个虚拟环境，不复用 .venv。本机已于 2026-09-29 建好。

    不要直接跑 install_pico.sh——它有两处会咬人
    • 多拉几 GB：torch>=2.4.0 是 gear_sonic 的基础依赖（不在 extra 里），而脚本全程没有预装 CPU 版。实测解析出 torch==2.14.0 CUDA 版 + 15 个 nvidia-* 包 + triton，共 53 个包。先装 CPU 版只有 151.9 MiB。
    • 夹着一次 dpkg -i：第 8 步装 PC Service，系统级改动。它整个块可以用 SKIP_PC_SERVICE=1 跳过。
    项目自己的 docs/x2/README.md 与 CLAUDE.md 第三节都写了「torch 必须先装 CPU 版」，是这个脚本漏了这步。 
    cd /home/nvidia/Documents/czq/GR00T-WholeBodyControl-X2
export PATH="$HOME/.local/bin:$PATH"
uv python install 3.10
uv venv .venv_teleop --python "$(uv python find --no-project 3.10)" --prompt gear_sonic_teleop
VPY=$PWD/.venv_teleop/bin/python
# ★ 脚本漏掉的关键一步：
uv pip install --python "$VPY" torch --index-url https://download.pytorch.org/whl/cpu
uv pip install --python "$VPY" -e "gear_sonic[teleop]"
uv pip install --python "$VPY" cmake pybind11 setuptools
export CMAKE_PREFIX_PATH="$("$VPY" -m pybind11 --cmakedir)"
uv pip install --python "$VPY" --no-build-isolation \
  -e external_dependencies/XRoboToolkit-PC-Service-Pybind_X86_and_ARM64/
    本机实测结果（可直接对照） 39 个包，零 nvidia-*、零 triton，torch 2.14.0+cpu，xrobotoolkit-sdk 1.0.2 由预编译 so 编出（7 秒）。
    两个可跳过项：aarch64 的 libPXREARobotSDK.so 仓库里已自带（19.6 MB），省掉源码编译；SKIP_SIM_AND_UNITREE=1 可再省掉 CycloneDDS 源码编译——laptop 半边只发 intent，不需要 mujoco 和 unitree DDS。
    验证隔离性：pyvenv.cfg 里 include-system-site-packages = false，且 .venv_teleop/bin/python3 直指 xr-env（不经 .venv）——所以它和 .venv 是同一种耦合：删掉 xr-env 会连带弄坏这两个 venv。

  • 这是个查不出来的静默陷阱，已经在本机实测确认。三件事同时成立：

    • 1run_pico_teleop.sh 第 23 行期望 /opt/apps/roboticsservice；这个目录在本机不存在。
    • 2第 103 行的检查是 pgrep -x RoboticsService，只按进程名匹配。
    • 3而 czq/roboticsservice/ 起的那个 ./RoboticsServiceProcess 正在跑，于是这个检查被"满足"了，缺失的目录永远不会被报出来。

    三条路里，实测答案是 C——而且 A 和 B 都跑不通：

    • A
      照 install_pico.sh 走，dpkg -i 装到 /opt/apps/roboticsservice。和红线冲突，且实测装上也跑不起来（原因见下）。
    • B
      把 deb 解到 czq/ 下，用环境变量指过去，系统一点不动。解包本身没问题，但解出来的二进制在本机也跑不起来。 
      dpkg-deb -x /home/nvidia/Documents/czq/GR00T-WholeBodyControl-X2/gear_sonic_deploy/thirdparty/roboticsservice_1.0.0.0_arm64.deb \
  /home/nvidia/Documents/czq/pico_service
    • C
      实际生效的方案：用 czq/roboticsservice/ 那份正在跑的守护进程。它已经在 :60061 上监听，run_pico_teleop.sh 会直接走「already running」分支，什么都不用配。
    2026-09-29 实测：为什么 A 和 B 都跑不起来 解包出来的二进制 ldd 缺 libicuuc.so.70 / libicui18n.so.70：这个 deb 是 Ubuntu 22.04 的构建（ICU 70），而本机是 ICU 74。解包树的 lib/ 只有 15 个文件、不含 ICU。而 czq/roboticsservice/ 那份的 lib/ 自带 12 个 ICU，所以它能跑。
    也就是说：B 方案的价值不在于「换一条路装上了」，而在于它挡住了一次 dpkg -i——那个 deb 装进系统同样是跑不起来的二进制。
    陷阱本身仍然要记住 :60061 只能被一个进程占，而 pgrep -x 只按进程名匹配、不校验路径。所以「谁在跑」这件事被静默地决定了，脚本永远不会抱怨。
    写部署文件时如果加了「确保 PC Service 在跑」这类逻辑，只 pgrep 进程名是不够的——必须校验你期望的那个路径下进程真的可执行，否则这个陷阱会跟着你进真机。

  • 腰一个、两踝各一个。少一个就是残缺的全身解。

    配对顺序有讲究 头显里打开 Motion Tracker app 后，先把 max tracker usage 改成 3，再去配对腰和两个踝。这个值默认是 2，先配对就会卡在「只配上两个」，而且看不出是被设置挡住的。

  • 设完 tracker 数量、配对完，选 Full body 模式，然后点 Calibrate。

    每次重启都要重来 头显一重启，标定就没了。判断方法看按钮上的字：显示 Calibrate 说明标定已丢，显示 Recalibrate 才是还有。每次重启头显之后都要重新标定，不然 body 会一直是 False。

  • 看三件事：身体数据可用、时间戳在走、tracker 数量是 3。

    .venv_teleop/bin/python -c "import xrobotoolkit_sdk as xrt, time; xrt.init(); time.sleep(2); print('body:', xrt.is_body_data_available(), 'stamp:', xrt.get_time_stamp_ns(), 'trackers:', xrt.num_motion_data_available())"
    本机实测（2026-09-29，无头显）——「连不上」和「没数据」要分清 链路半边已确认通过，日志里能看到 SDK 真的连上了守护进程： 
    initialize sdk, connect 127.0.0.1:60061
client start
server stream server connect
server connect watch server feedback thread start
    没有头显时 stamp: 0、body: False 是正常的，不是故障——身体数据来自头显。所以无头显时这条的判据只有「能连上 :60061」；后两项要戴着头显才有意义。
    实测到的一个真实异常：退出时会核心转储 上面这条命令跑完，进程以 terminate called without an active exception 中止。pybind SDK 在解释器拆卸时没有 join 自己的反馈线程，析构时触发 std::terminate。
    为什么要在意：C++ 的 terminate 会跳过 Python 的 atexit。如果 tape 录制是挂在 atexit 上落盘的，每次 live session 都可能留下一个没写完的 tape。跑完真机或长回放后，去 tape 目录确认文件能正常 np.load。
    时序 不要和 sender 同时跑。两个 xrt 会话会互相干扰。（仿真栈自己那个 C++ deploy 不占 xrt 会话，所以栈跑着的时候跑这条没问题——前提是 run_pico_teleop.sh / live_pico_smpl_teleop.py 没有在跑。）

  • 戴头显之前，先把「除头显之外的一切」验掉。仓库自带一段 Pico 录制，直接灌进正在跑的仿真栈，不需要头显、不需要 tracker。这是 F05 定义的 headset-free 门禁。

  --tape-replay gear_sonic/data/motions/x2_pico_chores/tapes/session_20260917_014453Z_x2_seg02.npz \
  --auto-engage

    deploy 侧出现：WHOLE-BODY ENGAGED — smpl head (crossfade 0.40s)。
    仿真侧：grav_z ≈ -1.00（直立没倒）、wrist_bypass_max_dev_rad 持续增长（参考在动、机器人在跟）。
